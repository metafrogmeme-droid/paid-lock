# Claw Pay integration note (design only)

How Claw Pay's gate can enforce `paid.lock` at pay time with `@paid-lock/runtime`. This is a design note: no code
goes into Claw-Pay from this repository (CLAUDE.md §3 item 9, §5 rule 12). Claw Pay decides if and when to adopt it.

Read from `metafrogmeme-droid/Claw-Pay` @ `f1bd144` (main, 2 Nov 2026), read-only: `packages/core/src/types.ts`
(`PaymentIntent`), `packages/core/src/decide.ts` (`decide`, `Decision`), `packages/core/src/reasons.ts`,
`packages/x402/src/parse.ts` and `intent.ts`, `docs/DECISIONS.md` (x402 parser entry), `docs/ARCHITECTURE.md`.

## Where things stand

- Claw Pay's x402 **parser** has landed (`parseV2Header`, `parseV1Body` → `PaymentRequirements`, then
  `toPaymentIntent`). Its x402 **gate** (fetch wrapper, probe, signing) is Claw Pay's M3 (13 Nov) and does not exist
  yet. Claw Pay's DECISIONS names `@x402/core` 2.29.0 as the candidate for signing there.
- `@paid-lock/runtime` (M5, this repo) offers `checkAgainstLock`, `checkSelected`, `checkResponse`, `allows`,
  `loadLock(path, { expectedDigest })` and an adapter for the `@x402/core` client hooks (SPEC "Runtime library").
- Both projects are MIT. The runtime's production dependencies are `zod` and `@noble/hashes`; it has no wallet or
  signing library (dependency allowlist test).

## What each side checks

The two checks overlap little; together they cover more than either alone.

| Question at pay time                                                                             | Claw Pay `decide()`                                       | paid.lock                                                                                     |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Is this seller and `payTo` on the owner's list?                                                  | `SELLER_NOT_LISTED`, `PAYTO_MISMATCH` (hand-written list) | `NOT_IN_LOCK`, `PAYTO_CHANGED` (pinned per endpoint)                                          |
| Network and asset                                                                                | allowed sets (`NETWORK_NOT_ALLOWED`, `ASSET_NOT_ALLOWED`) | the exact pinned ones (`NETWORK_CHANGED`, `ASSET_CHANGED`)                                    |
| Price                                                                                            | per-call, per-seller and daily caps, quote drift          | per-option maximum (`PRICE_ABOVE_LOCK`)                                                       |
| Payments per day, pause, expiry, paid-no-result hold, deny lists, confirm threshold              | yes                                                       | no                                                                                            |
| Scheme, payment flow, resource URL, protocol version                                             | scheme only checked to be present                         | `SCHEME_CHANGED`, `PAYMENT_FLOW_CHANGED`, `RESOURCE_URL_MISMATCH`, `PROTOCOL_VERSION_CHANGED` |
| Any other change in the terms (`extra`, `maxTimeoutSeconds`, extensions, new or removed options) | not modelled (the parser keeps only modelled fields)      | `TERMS_CHANGED_OTHER`, `NEW_OPTION_OFFERED`, `OPTION_REMOVED`                                 |
| Where the list comes from                                                                        | the owner writes rules                                    | generated by `paid-lock add`, reviewed as a git diff, checked in CI daily                     |

## Proposed wiring (for Claw Pay's M3 gate)

One gate decision per payment, one receipt:

```
unpaid request ─▶ 402 ─┬─ Claw Pay: parseV2Header / parseV1Body ─▶ toPaymentIntent(selected accept) ─▶ decide()
                       └─ paid.lock: checkAgainstLock(lock, method, requestUrl, paymentRequired)
                                     + checkSelected(lock, method, requestUrl, paymentRequired, selected)
                                                        │
                         outcome = the stricter of the two ─▶ sign only if ALLOWED (or owner OK, see below)
```

1. **Same bytes, same URL.** Both checks read the same 402 and use the URL the agent requested, never the 402's own
   `resource.url` (Claw Pay's `IntentContext.sellerOrigin` already follows this; paid.lock's adapter does too,
   DECISIONS D-024). paid.lock needs the decoded `PaymentRequired` **object** (or the raw response through
   `checkResponse`), not Claw Pay's normalised `PaymentRequirements`: the normalised form drops `extra`,
   extensions and other fields that the terms hashes cover.
2. **Stricter outcome wins.** Claw Pay's `ALLOWED | NEEDS_OWNER_OK | BLOCKED` and paid.lock's
   `allowed | needsOk | blocked` map one to one. The gate takes the stricter outcome and shows that side's verdict
   line; both sides only ever produce the three verdict strings, so nothing new is shown to users.
3. **Parser differences fail closed.** paid.lock refuses some inputs Claw Pay's parser accepts (for example
   duplicate JSON keys, where parsers disagree on which value wins). Then paid.lock says
   `REQUIREMENTS_UNREADABLE`, the stricter outcome is Blocked, and no payment is made.
4. **Owner OK.** A paid.lock "Needs your OK" can go to Claw Pay's owner OK queue like `NEEDS_OWNER_OK`. Approving
   it allows that one payment; it does not change `paid.lock` (that stays a reviewed `paid-lock update` in the
   agent's repo). A paid.lock "Blocked" is never cleared by an owner OK, matching Claw Pay's rule that approval
   clears only `NEEDS_OWNER_OK`, never a block.
5. **Receipts.** Record both codes, e.g. `{ clawPay: "OK", paidLock: "TERMS_CHANGED_OTHER" }`, plus the lock
   digest (`paid-lock digest`), so a receipt says which reviewed lock the payment was checked against.
6. **Which lock.** The gate loads the agent repo's `paid.lock` once at start-up with
   `loadLock(path, { expectedDigest })`, the digest set at deploy time (P-04). An endpoint that is not in the lock
   is Blocked (`NOT_IN_LOCK`); if Claw Pay wants paid.lock as an optional layer, the gate can skip it per seller,
   but that choice belongs in Claw Pay's rules, not in paid.lock.
7. **If the gate uses the `@x402/core` client.** `installPaidLock({ client, http }, lock)` registers the two hooks
   directly and aborts the payment with the verdict line. That is the simplest path, but it runs separately from
   `decide()`: an abort from either stops the payment, and the owner OK queue would not see paid.lock's "Needs your
   OK". For one decision and one receipt, call `checkAgainstLock` and `checkSelected` inside Claw Pay's own
   before-payment hook instead (point 2), and add that hook to Claw Pay's guard-reach lint.

## Checks Claw Pay could add when it integrates

- A contract test: the shared fixture set (the demo's named changes, `fixtures/mock-seller` `FORECAST_VARIANTS`)
  through the gate gives the same paid.lock verdicts as `paid-lock verify`, and the mock seller sees no payment
  header on any Blocked or Needs-your-OK case.
- Guard reach: every pay path in the gate calls both `decide()` and a paid.lock check.

## Proposal (not scope): one shared x402 parser

Both projects now parse x402 v2 and v1 with similar limits (128 KiB header, 1 MiB body, depth 64) but different
outputs: Claw Pay keeps only modelled fields; paid.lock keeps everything and hashes it. A shared, MIT,
dependency-light parser package could serve both (normalised fields for rules, raw remainder for hashing).
Trade-offs: one place to fix parser bugs and one fuzz corpus, against coupling two release cycles before either
has users. Cost about 1.5 days, risk medium (two consumers). Better after both have shipped 0.1.0; the owner decides.
